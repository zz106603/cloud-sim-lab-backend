# RDS Multi-AZ

## 왜 필요한가

RDS Multi-AZ는 운영 DB를 여러 가용 영역에 배치하고 장애 발생 시 대기 인스턴스 또는 다른 DB 인스턴스로 자동 장애 조치할 수 있게 합니다. 데이터 복구 가능성뿐 아니라 서비스 중단 시간을 줄여야 할 때 검토하는 가용성 선택지입니다.

## 정상 요청과 장애 조치 흐름

```text
정상: EC2 -> RDS 엔드포인트 -> Primary DB
장애: Primary 장애 감지 -> 자동 장애 조치 -> 엔드포인트 대상 변경
     -> 애플리케이션 재연결 -> 요청 재개
```

애플리케이션은 같은 RDS 엔드포인트를 사용하지만 장애 조치 중 기존 연결이 끊기고 잠시 연결 또는 쿼리가 실패할 수 있습니다.

## 운영 예시

단일 AZ RDS 장애로 쓰기와 조회가 모두 중단되고 수동 복구에 오래 걸렸다면 Multi-AZ가 적합한 대응일 수 있습니다. 반면 조회 트래픽이 많아 CPU를 분산하려는 목적이라면 Read Replica가 더 직접적인 선택입니다.

## 장애 상황

- 장애 조치 중 커넥션 풀에 남은 기존 연결이 실패할 수 있습니다.
- DNS 캐시를 지나치게 오래 유지하면 변경된 대상을 늦게 따라갈 수 있습니다.
- 애플리케이션 재시도와 타임아웃이 부적절하면 DB가 복구된 뒤에도 장애가 길어질 수 있습니다.
- Multi-AZ를 사용해도 잘못된 쿼리나 논리적 데이터 삭제는 자동으로 복구되지 않습니다.

## Backup, Multi-AZ, Read Replica 비교

| 선택 | 주목적 | 해결하지 못하는 문제 |
| --- | --- | --- |
| Backup | 특정 시점 데이터 복구 | 즉시 장애 우회 |
| Multi-AZ | DB 인프라 장애 시 자동 장애 조치 | 읽기 성능 확장 |
| Read Replica | 읽기 부하 분산 | 기본 구성에서 쓰기 DB 자동 장애 조치 |

## Trade-off

Multi-AZ는 가용성과 복구 시간을 개선하지만 추가 비용이 발생합니다. 또한 자동 장애 조치가 애플리케이션 오류를 완전히 없애는 것은 아니므로 재연결과 제한된 재시도 설계가 필요합니다.

## 실무 주의점

- 장애 조치 시간을 가정하지 말고 정기적으로 테스트합니다.
- 커넥션 풀, DNS 캐시, 타임아웃이 장애 조치를 따라가는지 확인합니다.
- Multi-AZ와 별도로 백업 보존 및 복구 절차를 준비합니다.
- 목표 복구 시간과 허용 비용을 기준으로 도입 여부를 판단합니다.
