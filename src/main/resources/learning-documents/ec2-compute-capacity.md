# EC2와 컴퓨팅 용량

EC2는 Spring Boot 같은 애플리케이션이 실제 요청을 처리하는 컴퓨팅 자원입니다.

## 왜 필요한가

애플리케이션 서버는 요청을 파싱하고 비즈니스 로직을 실행하며 RDS, Redis, 외부 API와 통신합니다. EC2 용량이 부족하면 이 모든 단계가 느려질 수 있지만, 응답 시간이 느리다는 이유만으로 EC2를 증설하면 실제 병목이 RDS나 외부 API일 때 비용만 늘어납니다.

## 요청 흐름

```text
Client -> EC2(Spring Boot) -> RDS 또는 Redis -> EC2 -> Client
```

단일 EC2 구조에서는 모든 요청과 배포가 한 인스턴스에 집중됩니다. CPU 사용률, 메모리, 스레드 풀 대기, GC 시간, 응답 시간을 함께 확인해 애플리케이션 계층이 병목인지 판단해야 합니다.

## 운영 예시

이벤트 시작 후 EC2 CPU와 응답 시간이 함께 상승하고 RDS CPU는 안정적이라면 컴퓨팅 용량 부족 가능성이 큽니다. 인스턴스 사양을 키우는 scale-up은 빠르게 적용할 수 있지만 한계가 있고 단일 장애 지점을 없애지 못합니다. ALB 뒤에 여러 EC2를 두는 scale-out은 처리량과 가용성을 높이지만 애플리케이션을 상태 비저장으로 운영해야 합니다.

## 장애 상황

- 단일 EC2가 재시작되거나 장애가 나면 전체 API가 중단됩니다.
- 배포 중 애플리케이션 재시작이 발생하면 요청을 처리할 다른 서버가 없습니다.
- 로컬 디스크나 메모리에 세션을 저장하면 여러 EC2로 확장했을 때 요청마다 상태가 달라질 수 있습니다.

## Trade-off

| 선택 | 장점 | 한계 |
| --- | --- | --- |
| Scale-up | 적용이 빠르고 구조 변경이 적음 | 비용 증가, 용량 한계, 단일 장애 지점 유지 |
| Scale-out | 처리량과 장애 우회 능력 향상 | ALB, 배포, 세션 관리 복잡도 증가 |
| 현 상태 유지 | 비용과 운영 복잡도 최소 | 트래픽 증가와 장애에 취약 |

## 실무 주의점

- CPU만 보지 말고 메모리, GC, 스레드 풀, 의존 서비스 지연을 함께 확인합니다.
- Auto Scaling을 사용할 때는 시작 시간과 Health Check 통과 시간을 고려합니다.
- 세션, 업로드 파일, 임시 상태를 EC2 로컬에 의존하지 않도록 설계합니다.
- scale-up과 scale-out 모두 부하 테스트로 실제 병목이 개선되는지 검증합니다.
