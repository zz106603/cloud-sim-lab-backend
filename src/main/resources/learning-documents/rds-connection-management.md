# RDS와 연결 관리

## 왜 필요한가

RDS는 애플리케이션 데이터의 중심 저장소이고, Spring Boot 애플리케이션은 보통 커넥션 풀을 통해 RDS에 쿼리를 보냅니다. DB 연결은 제한된 자원이므로 트래픽이 늘 때 애플리케이션 인스턴스 수, 풀 크기, 쿼리 실행 시간, RDS 최대 연결 수를 함께 관리해야 합니다.

## 요청 흐름

```text
Client -> EC2 애플리케이션 -> 커넥션 풀 -> RDS
```

요청은 풀에서 연결을 빌리고 쿼리를 실행한 뒤 연결을 반환합니다. 연결 반환이 늦거나 쿼리가 오래 실행되면 풀 대기가 증가하고, 사용자는 DB CPU가 한계에 도달하기 전에도 느린 응답을 경험할 수 있습니다.

## 운영 예시

EC2를 2대에서 10대로 확장하면서 각 인스턴스의 최대 풀 크기를 50으로 유지하면 애플리케이션이 최대 500개 연결을 시도할 수 있습니다. RDS가 이를 감당하지 못하면 연결 거부와 타임아웃이 발생합니다. 단순히 풀을 크게 늘리는 대신 느린 쿼리, 트랜잭션 범위, 인스턴스 수를 함께 고려해야 합니다.

## 확인할 지표

- DB CPU와 메모리
- 현재 연결 수와 최대 연결 수
- 커넥션 풀 활성, 유휴, 대기 연결 수
- slow query, lock wait, 트랜잭션 시간
- 연결 획득 및 쿼리 타임아웃

## 장애 상황

- 풀 크기가 너무 작으면 RDS에 여유가 있어도 요청이 연결을 기다립니다.
- 풀 크기가 너무 크면 RDS가 연결과 동시 쿼리로 포화됩니다.
- RDS 재시작이나 Multi-AZ 장애 조치 시 기존 연결이 끊기고 일시적인 오류가 발생합니다.
- 무제한 재시도는 장애 중 RDS에 더 큰 부하를 줄 수 있습니다.

## Trade-off

큰 풀은 짧은 피크의 대기를 줄일 수 있지만 DB 포화 위험을 높입니다. 작은 풀은 DB를 보호하지만 애플리케이션 대기가 길어질 수 있습니다. RDS Proxy는 연결 급증을 완화할 수 있지만 추가 비용과 동작 특성을 이해해야 합니다.

## 실무 주의점

- 연결 획득, 쿼리, 트랜잭션 타임아웃을 목적에 맞게 구분합니다.
- 재시도는 횟수 제한과 지수 백오프를 사용하고 멱등성을 확인합니다.
- Auto Scaling 최대 인스턴스 수를 기준으로 총 연결 가능량을 계산합니다.
- 장애 조치 후 커넥션 풀이 새 연결을 정상적으로 만드는지 테스트합니다.

## 면접 질문
